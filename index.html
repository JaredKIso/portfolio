Case study · DotHub

A "flaky" build that was really a race condition

DotHub's first Docker build failed at random, and a retry usually passed. Retrying until it goes green is the easy answer. The error message pointed at something real.

  1. report

    The problem

    Some builds stopped with SQLITE_BUSY: database is locked while collecting page data. It depended on timing, so it looked like noise.

  2. manage_search

    The diagnosis

    The build imports every route, so 15 workers opened the same fresh SQLite file at once and raced to switch it to WAL mode. The losers failed, even with a 5-second busy timeout.

  3. build

    The fix

    During the build, each worker gets its own empty, migrated in-memory database. The build has no data to read, so there's nothing to share.

  4. verified

    The result

    15 → 0

    Workers sharing a database file during the build, so the lock can't happen. A 9-line change.

backup DotHub

Backups that left junk behind

SQLite's backup API wrote each copy in WAL mode, and the read-only connection that checked it couldn't clean up its -wal and -shm files on close. Every day left an orphaned pair that pruning never removed. The check now switches the copy to a rollback journal first, and old leftovers get swept, with tests.

Hunting a leak, finding weight

Thousands of requests with forced garbage collection and heap-snapshot diffs, plus 30 laps of in-browser navigation, found no memory leak. They did find a validation library riding into the browser, a Markdown renderer loading on every page, and a rate limiter that grew with every one-off visitor.
